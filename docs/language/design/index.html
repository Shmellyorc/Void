VOID Language

Its own language.
Its own direction.

VOID borrows useful familiarity from established syntax while keeping its compiler, runtime, libraries, native model, and tooling architecture independent.

Familiarity is a starting point, not the identity.

VOID uses C#-inspired syntax because that style is productive for game code. It is independently designed, owns its own parser/semantics/runtime, and compiles to native code through C.

Focused does not mean artificially small.

VOID is intentionally game-focused, but that does not mean stripping away the language features larger projects rely on. The boundary is the domain, not an artificial cap on expressiveness.

Familiar object semantics should compose normally.

Object features are expected to compose. A type should be able to inherit behavior, satisfy interfaces, publish events, use generics, and participate in GC without each capability creating a separate set of rules.

Value semantics should survive real composition.

Value types should keep their semantics even when stored in arrays, captured by closures, suspended by iterators, or carrying managed references. The compiler tests those combinations because real game code crosses those boundaries constantly.

Cleanup is part of control flow.

Exceptions, deterministic disposal, iterators, and structured exits all pass through one cleanup and unwinding model. Resource lifetime is part of control flow, so GC-root restoration and pending cleanup cannot be skipped just because execution leaves a scope unexpectedly.

Abstractions should reuse existing dispatch.

Extension methods reuse overload resolution, constrained static calls reuse monomorphized generics, and default interface methods reuse the interface system. New syntax should not create a second call model when the compiler already has one that can express the behavior.

Flow-sensitive syntax should reuse normal semantics.

Patterns should feel like an extension of ordinary type and property semantics, not a separate mini-language. is, switch cases, guards, and switch expressions therefore share the same matcher and flow rules.

Generic lowering must preserve why code was legal.

Constrained operators are authorized by generic interface contracts before specialization. Iterator and closure transformations preserve that generic origin and constraint provenance when locals become generated fields, rather than letting transformed concrete types silently lose the semantic contract that permitted the operation.

Conversions should be selected once.

Standard, user-defined, nullable-lifted, target-typed, and constrained generic conversions now share one semantic classifier/resolver. Lowering consumes the selected conversion and its generic-contract provenance instead of widening legality after specialization.

One semantic model should serve every tool.

The compiler is the source of truth for both builds and editor intelligence. voidc check and voidc lsp ask the same parser, project model, and semantic engine for answers, so an editor does not need a second language implementation hidden inside a plugin.

Close real restrictions, not roadmap vanity metrics.

Completion work is driven by the places ordinary game code still hits a real compiler restriction or integration failure. The roadmap stays phase-based so progress is measured by removing meaningful boundaries, not by inflating an internal milestone count.

Use standard native mechanisms where they fit.

VOID prefers standard native mechanisms when they already solve the problem. Portable C, normal system toolchains, the C ABI, static archives, and standard debug mappings keep the low-level path understandable instead of inventing custom machinery without a reason.

Engine and Language remain separate.

VOID Engine and VOID Language are designed to complement each other while remaining distinct projects. The Engine keeps its current C#/.NET foundation, and the Language remains independently useful.

Thin editor clients. The compiler-side voidc lsp now owns the language intelligence needed for diagnostics, hover, completion, navigation, references, and symbols. A future VS Code extension can focus on launching/connecting, language registration, editor integration, and packaging instead of duplicating the lexer, parser, or semantic model.

A foundation, not a cage.
